# آیا «Monad» می‌تواند entity بنیادینِ ریشه‌ی همه‌ی entityها باشد؟ — ارزیابی

تاریخ: 2026-09-21 · Origin: ENGINEERING_DECISION (پیشنهاد، هنوز تصمیم نیست)

## وضعیت فعلی
پنج entity ذخیره‌شونده داریم و هیچ ریشه‌ی مشترکی ندارند:

| entity | فایل | شناسه | زمان ساخت | وضعیت | origin class |
|---|---|---|---|---|---|
| Claim | knowledge/store.py | `id` (uuid) | `created` | `status` | ✅ دارد |
| SkillSpec | skills/registry.py | `name` | `recorded` | `status` | ❌ |
| AgentSpec | agents/factory.py | `name` | `created` | `status` | ❌ |
| Product | factory/software.py | `name` | `created` | `stage` + `outcome` | ❌ |
| IterationRecord | core/loop.py | `number` | `started` | — | ❌ |

یک مفهوم («کِی ساخته شد») با چهار نام مختلف. و قانون اساسی می‌گوید «هر گزاره‌ی ذخیره‌شده دقیقاً یک origin class دارد» — ولی فقط Claim به آن پایبند است.

## پاسخ کوتاه
بله، و دلیلش زیبایی یا فلسفه نیست؛ دو دلیل عینی است:
1. **اجرای قانون اساسی**: origin class باید روی *هر* چیز ذخیره‌شده باشد، نه فقط Claim.
2. **حذف تکرار**: چهار نام برای یک فیلد، سه نوع شناسه.

## شکل حداقلی (اگر تصمیم گرفته شد)
```python
# monad/core/monad.py
@dataclass(kw_only=True)
class Monad:
    id: str = field(default_factory=lambda: uuid.uuid4().hex[:12])
    origin: str = "ENGINEERING_DECISION"
    created: str = field(default_factory=_now)
    status: str = "OPEN"
```
بقیه از آن ارث می‌برند و فیلدهای تکراری‌شان حذف می‌شود. `kw_only=True` لازم است تا ترتیب فیلدهای default/non-default در ارث‌بری dataclass نشکند (Python ≥3.10، که pyproject همین را می‌خواهد).

## هزینه‌ی واقعی
- **مهاجرت داده**: ۶۰ خط JSONL در `data/` با نام‌های قدیمی (`recorded`, `started`). یک اسکریپت ۱۰ خطی یا خواندنِ tolerant.
- **سازگاری Mizan**: `products/mizan/test_mizan.py` مستقیماً `Claim(**r)` می‌سازد؛ Claim نباید فیلدی از دست بدهد.
- **وسوسه‌ی افزودن رفتار**: ریشه باید فقط *فیلد* باشد، نه رفتار مشترک (serialize، validate، history). آن‌ها وقتی اضافه می‌شوند که سه entity واقعاً یک رفتار مشترک بخواهند.

## چه چیزی نباید باشد
- خودِ MONAD (سیستم) یک instance از این کلاس نیست. `Monad` یعنی «واحد ذخیره‌شدنیِ پایه»، نه «کل سیستم». اگر اسم گیج‌کننده است، `Entity` یا `Unit` هم قابل قبول است؛ اسم را مؤسس تعیین می‌کند.
- IterationRecord شاید جایش نباشد: رکورد اجرای حلقه است، نه گزاره‌ای درباره‌ی جهان. با origin=EMPIRICAL_RESULT جا می‌گیرد، ولی اجبار نیست.

## پیشنهاد
انجام بدهیم، در یک iteration، با این ترتیب: ۱) کلاس ریشه + تست ۲) ارث‌بری Claim (بدون تغییر رفتار، تست Mizan سبز) ۳) بقیه یکی‌یکی + مهاجرت داده ۴) گزارش مقایسه با iteration قبل (Article 14).

## پرسش دوم: با هزاران موجودیت، آیا «هر چیز یک مناد است»؟

بله. این همان الگوی «همه‌چیز یک object است» (Smalltalk، Python) است و Python همین الان آن را انجام می‌دهد: هر کلاس از `object` ارث می‌برد. مناد فقط یک `object` با چهار فیلدِ قانون‌اساسی است.

دو معنای «ریشه» را جدا نگه داریم:
1. **ریشه‌ی نوعی** (type root): `Monad` کلاس پدرِ همه است. هر موجودیت *یک مناد است*. این همان پیشنهاد بالاست.
2. **ریشه‌ی نمونه‌ای** (instance root / «Monad core»): خودِ سیستم هم یک مناد ذخیره‌شده است (مناد شماره‌ی ۰) که به قانون اساسی، نسخه، و وضعیتش لینک دارد. اختیاری است؛ قشنگ است ولی الزامی نیست.

چه چیزی واقعاً به‌دست می‌آید وقتی همه مناد باشند:
- **ارجاع یکنواخت**: `evidence`, `skills`, `constraints` همه فهرست id مناد می‌شوند، نه رشته‌ی نام. کل داده یک گراف می‌شود.
- **یک قانون برای همه**: origin، staleness، reversibility (Article 12–14) یک‌بار روی ریشه نوشته می‌شود.
- **یک store**: به‌جای ۵ فایل JSONL، یک فایل با فیلد `kind` (یا همان ۵ فایل، ولی با فرمت مشترک). انتخاب هر دو معتبر است.

خطر اصلی: **فروپاشی نوع‌ها**. اگر ریشه به «کیسه‌ی خصوصیات» (`props: dict`) تبدیل شود، هزار موجودیت می‌شود هزار blob بی‌شکل و همه‌ی validateها می‌میرند. قاعده: ریشه ثابت و کوچک؛ هر `kind` یک subclass تایپ‌شده با فیلدهای خودش. «خصوصیات و پارامترهای مختلف» = subclass، نه dict.

فلسفه (لایب‌نیتس: مناد واحد تقسیم‌ناپذیر که کل را بازتاب می‌دهد) استعاره‌ی خوبی است ولی در کد نمی‌آید؛ همان قرنطینه‌ی research-notes.

## پرسش سوم: دیتابیسی که ده‌ها سال رشد کند چه ساختاری دارد؟

اول یک واقعیت: «هزاران موجودیت» از نظر حجم هیچ است. یک فایل متنی آن را حمل می‌کند. آنچه ده‌ها سال را می‌سازد **فرمت و معناشناسی رکورد** است، نه موتور دیتابیس. موتورها عوض می‌شوند؛ رکورد باید بدون موتور خواندنی بماند.

### ۶ اصل (هر کدام با پشتوانه‌ی قانون اساسی)
1. **منبع حقیقت = لاگ append-only.** هیچ رکوردی ویرایش یا حذف نمی‌شود؛ تغییر = رکورد جدید با `supersedes: <id قبلی>`. (Article 12, 13) — هر جدول، ایندکس، گراف یا embedding از این لاگ *بازسازی‌پذیر* است و قابل دورریختن.
2. **یک شکل رکورد برای همه** (همان مناد): `id, kind, origin, created, status, supersedes, source` + بدنه‌ی تایپ‌شده‌ی kind. ریشه ثابت؛ kindها آزاد.
3. **رابطه‌ها هم مناد هستند.** `link(from, to, relation, origin, created)` یک رکورد است، نه ستون. evidence، contradicts، skills، constraints همه link می‌شوند → کل داده یک گراف است که هر یالش provenance دارد.
4. **شناسه بی‌معنا و ابدی.** uuid یا hash محتوا. هرگز بازاستفاده نمی‌شود، هرگز معنا حمل نمی‌کند (نام و شماره فیلد هستند نه id).
5. **تکامل schema فقط افزایشی.** فیلد اضافه می‌شود، هرگز حذف/بازنام نمی‌شود؛ هر رکورد `schema: N` دارد؛ خواننده فیلد ناشناخته را نادیده می‌گیرد؛ هر migration یک اسکریپت در git است.
6. **فرمتِ ذخیره باید بدون نرم‌افزار ما خواندنی باشد.** JSONL و SQLite هر دو این شرط را دارند (SQLite فرمت توصیه‌شده‌ی Library of Congress برای نگهداری بلندمدت است و تا ۲۰۵۰ تضمین سازگاری دارد). Postgres، Neo4j، vector DB ندارند → فقط به‌عنوان ایندکس مشتق.

### مسیر رشد (بدون تغییر رکورد)
| مرحله | موتور | کِی |
|---|---|---|
| حالا | JSONL در git (همین) | تا ده‌ها هزار رکورد |
| بعد | SQLite، یک فایل، stdlib، دو جدول: `monads(id, kind, origin, created, status, supersedes, body JSON)` و `links(from_id, to_id, relation, origin, created)` | وقتی query/جوین لازم شد یا فایل از چند MB گذشت |
| دور | Postgres (چند نویسنده/شبکه) یا هر چیز دیگر پشت همان Store | وقتی یک پروسه کافی نبود |

در هر مرحله لاگ JSONL می‌ماند (export روزانه/کامیت git) و موتور فقط *ایندکس* است. اگر موتور بمیرد، از لاگ می‌سازیم.

### چه چیزی نسازیم
- ORM، microservice، graph DB، vector DB به‌عنوان منبع حقیقت — همه مشتق‌پذیرند.
- schema-less «props dict» — همان فروپاشی نوع‌ها.
- interface چندموتوره *الان* — وقتی موتور دوم آمد، از دل KnowledgeStore فعلی بیرون کشیده می‌شود.

### گام عملی (اگر تصمیم گرفته شد)
همان ۴ فیلد ریشه + `supersedes` + `schema` روی Monad؛ جدول `links` به‌جای فهرست‌های نام؛ بقیه هیچ. JSONL می‌ماند.
